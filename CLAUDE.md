# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What we're building

An information system that automates the day-to-day work of a fitness club. It covers:

- **Clients**: full name, age, email (the required primary contact), optional phone, membership, and the membership's expiry date.
- **Visits**: every client check-in is recorded.
- **Trainers**: a profile for each trainer with specialization, work schedule, and client list.
- **Bookings**: sign-ups for group classes and individual sessions.
- **Membership plans**: configurable plans such as single visit, monthly, and yearly.
- **Expiry notifications**: clients are notified automatically before their membership expires.
- **Reports**: client list with visit activity, club revenue per month and year, and trainer and room load by day.

The source of truth for requirements is `docs/Requirements/Fitness Club System.md`.

## Repository map

Each folder has its own CLAUDE.md with the details for that area. This file covers only facts that apply across the whole project.

- `api/`: C# .NET backend API.
- `ui/`: React single-page app.
- `docs/`: Obsidian vault with requirements and code documentation.
- `deploy/`: Docker / docker compose deployment.

## Architecture

- The UI talks to the API over HTTP only. It never accesses data storage directly.
- The API owns all business logic, data storage, scheduled jobs (expiry notifications), and reports.
- Each service is built as its own Docker image, and docker compose runs the whole stack.

## Design and patterns

- The design notes are in `docs/Code/Design/`: `Use Cases.md` (use case diagram), `Class Diagram.md` (UML domain model and layers), `Architecture.md` (deployment, layers, sequence diagrams) and `Design Patterns.md` (GoF, GRASP, SOLID and how they work together). Diagrams are Mermaid.
- GoF patterns in use:
  - **Strategy:** `INotificationSender` (SendGrid or logging, picked in `AddInfrastructure()`), `TimeProvider`.
  - **Adapter:** `SendGridNotificationSender`, the EF Core repositories, the UI's `AccessTokenBridge`.
  - **Facade:** the `I{Name}Service` application services, one per area.
  - **Factory Method** (static factories): `Client.Register`, `Trainer.Hire`, `Notification.MembershipExpiring`, value objects' `Create`/`Of`.
  - **Command:** the Hangfire `ExpiryNotificationJob`.
  - **Chain of Responsibility:** `ExceptionToProblemDetailsHandler` in the ASP.NET Core pipeline, axios interceptors.
  - **Observer:** TanStack Query subscriptions and invalidation.
  - **Template Method** (template fill): `EmailTemplates`.
  - **Decorator** (tests): `CountingUnitOfWork`.
- Also Repository, Unit of Work, Aggregate, Value Object and Domain Service (DDD), and the GRASP and SOLID mapping in `Design Patterns.md`.
- New code follows the same patterns. A new delivery channel is a new `INotificationSender`. A new area gets an aggregate with a static factory, a repository, a service facade and a thin controller.
- When you add or rename an aggregate, service, endpoint, role or pattern, update the matching diagram in `docs/Code/Design/` too.

## Status

- **Backend (`api/`):** foundation built, and the whole domain model is in place: DDD aggregates, repositories and a unit of work behind enforced Clean Architecture boundaries. Every requirement has endpoints: membership plans, clients/memberships/visits, trainers, rooms, sessions/bookings, expiry notifications (Hangfire job, manual trigger only; email through Twilio SendGrid when `SendGrid:ApiKey` is set, otherwise only logged; email is every client's required primary contact; staff can also send a branded expiry reminder or a 10% promotion from a client's page) and reports. It runs on SQL Server only (locally through `deploy/docker-compose.yml`), and EF migrations create the schema and seed mock data. Demo users per role are in `docs/Code/Demo Data and Users.md`. Stack and commands are in `api/CLAUDE.md`. Each area has its own spec in `docs/Code/Specs/`, and `docs/Code/Requirements Coverage.md` maps requirements to endpoints.
- **UI (`ui/`):** the staff portal covers every requirement. It is React + Mantine, uses a client generated by Orval from the API's OpenAPI document, and signs in with Auth0. Stack, commands and conventions are in `ui/CLAUDE.md`, and the design is in `docs/Code/Specs/2026-10-07-ui-design.md`. Ask before adding a new UI library.
- **Design docs:** use case, class, architecture and sequence diagrams and the pattern catalogue are in `docs/Code/Design/` (see "Design and patterns").
- **Specs and plans:** design specs go in `docs/Code/Specs/` and implementation plans in `docs/Code/Plans/`, not in Superpowers' default `docs/superpowers/`.

When requirements or behavior change, update the matching note in `docs/`.
